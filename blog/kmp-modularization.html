Kotlin Multiplatform modularization: structure a KMP project that scales

One giant shared module works for the first few screens. Then builds slow down and everything depends on everything. Here's how to split a KMP project into features, layers and core modules, and keep it clean as it grows.

TL;DR

  • Split your KMP project by feature (games, favorites, profile) and by layer inside each feature (presentation, domain, data).
  • Shared infrastructure lives in core modules: network, database, design system, common utilities.
  • Follow two rules: features never depend on other features, and domain depends on nothing except core:common.
  • Move repeated Gradle setup into convention plugins, so a new module takes a few lines instead of 80.
  • Ship one iOS framework from the app module. Don't turn every module into its own framework.

Every KMP project starts the same way: one shared module where everything goes. It's perfect for the first few screens. Then the app grows, builds slow down, and a change to one screen recompiles everything. Here's how to split a Kotlin Multiplatform project into modules that scale, and the rules that keep it clean.

01 Why modularize at all?

A single shared module works until it doesn't. Splitting it up gives you four concrete wins:

⚡

Faster builds

Gradle only recompiles modules that changed, and their dependents. Touch one feature, rebuild one feature.

🧱

Real boundaries

If presentation can't see data, nobody can call the database from a screen "just this once".

👥

Team ownership

Different people can own different features without merge conflicts in one giant module.

The fourth win is specific to KMP: modules make it obvious which code is truly shared and which is platform-specific, because each module declares its own targets and source sets.

02 The structure: features × layers

This is the layout I use for real KMP apps, like Gamopedia in my Compose Multiplatform course:

gamopedia/
├── composeApp/            ← app entry: Android, Desktop, iOS framework
├── iosApp/                ← Xcode project, calls into composeApp
├── build-logic/
│   └── convention/        ← shared Gradle setup (convention plugins)
├── core/
│   ├── common/            ← dispatchers, Result types, utilities
│   ├── network/           ← Ktor HttpClient setup
│   ├── database/          ← SQLDelight driver and schema
│   └── designsystem/      ← theme, colors, shared components
└── feature/
    ├── games/
    │   ├── domain/        ← models, repository interfaces, use cases
    │   ├── data/          ← repository implementations, DTOs, mappers
    │   └── presentation/  ← screens and ViewModels
    └── favorites/
        ├── domain/
        ├── data/
        └── presentation/

Each layer has one job:

  • domain: pure Kotlin. Models, repository interfaces and use cases. No Ktor, no SQLDelight, no Compose.
  • data: implements the domain interfaces using core:network and core:database. DTOs never leave this module.
  • presentation: Compose Multiplatform screens and ViewModels. Talks only to the domain layer.
💡

Start smaller. For a new app, one module per feature (with packages for the layers) is fine. Split a feature into domain, data and presentation when it grows or gets a second developer.

The two rules that matter most:

  1. Features never depend on other features. If games needs something from favorites, move it into a core module or a small shared domain module. Otherwise you end up with circular dependencies and lose the build-speed win.
  2. Domain depends on nothing except core:common. That keeps your business logic easy to test in commonTest and impossible to tangle with frameworks.

Only the app module sees everything. It wires features together: navigation between screens, and the dependency injection graph.

04 Stop copy-pasting Gradle: convention plugins

With ten modules, you'll have ten nearly identical build.gradle.kts files: the same targets, the same Android SDK levels, the same dependencies. A convention plugin puts that setup in one place.

First, include a build-logic build and turn on type-safe project accessors:

pluginManagement {
    includeBuild("build-logic")
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}

// Lets you write projects.core.network instead of project(":core:network")
enableFeaturePreview("TYPESAFE_PROJECT_ACCESSORS")

include(":composeApp")
include(":core:common", ":core:network", ":core:database", ":core:designsystem")
include(":feature:games:domain", ":feature:games:data", ":feature:games:presentation")
include(":feature:favorites:domain", ":feature:favorites:data", ":feature:favorites:presentation")

Then write the plugin once:

class KmpLibraryConventionPlugin : Plugin<Project> {
    override fun apply(target: Project) = with(target) {
        with(pluginManager) {
            apply("org.jetbrains.kotlin.multiplatform")
            apply("com.android.library")
        }

        extensions.configure<KotlinMultiplatformExtension> {
            androidTarget()
            iosX64()
            iosArm64()
            iosSimulatorArm64()
            jvm("desktop")
        }

        extensions.configure<LibraryExtension> {
            compileSdk = 35
            defaultConfig.minSdk = 24
            // Namespace from the module path, e.g. com.example.feature.games.data
            namespace = "com.example" + path.replace(':', '.').replace('-', '_')
        }
    }
}
plugins {
    `kotlin-dsl`
}

dependencies {
    compileOnly(libs.android.gradlePlugin)
    compileOnly(libs.kotlin.gradlePlugin)
}

gradlePlugin {
    plugins {
        register("kmpLibrary") {
            id = "awh.kmp.library"
            implementationClass = "KmpLibraryConventionPlugin"
        }
    }
}

Now every module's build file is tiny and only says what's different about it:

plugins {
    id("awh.kmp.library")
}

kotlin {
    sourceSets.commonMain.dependencies {
        implementation(projects.feature.games.domain)
        implementation(projects.core.network)
        implementation(projects.core.database)
    }
}
📌

Newer Android Gradle Plugin versions add a dedicated com.android.kotlin.multiplatform.library plugin for KMP modules. The idea is the same: whichever plugin your project template uses, configure it once in the convention plugin.

05 Wiring it together with Koin

Each module exposes its own Koin module, and the data layer binds its implementations to the domain interfaces:

val gamesDataModule = module {
    singleOf(::GameRepositoryImpl) bind GameRepository::class
}
val gamesPresentationModule = module {
    viewModelOf(::GameListViewModel)
    viewModelOf(::GameDetailViewModel)
}

The app module is the only place that knows about every module, so it starts Koin with all of them:

fun initKoin(config: KoinAppDeclaration? = null) = startKoin {
    config?.invoke(this)
    modules(
        networkModule,
        databaseModule,
        gamesDataModule,
        gamesPresentationModule,
        favoritesDataModule,
        favoritesPresentationModule,
    )
}

Notice that games:presentation asks for a GameRepository interface. It never learns that GameRepositoryImpl exists. That's the boundary doing its job.

06 What about iOS?

This trips up a lot of teams: don't make every module its own iOS framework. Each Kotlin framework carries its own copy of the Kotlin runtime, and types from one framework aren't the same types as in another, so a Game from framework A can't be passed to framework B.

Instead, the app module produces one framework (often called ComposeApp or Shared), and every feature and core module is simply a dependency of it. If Swift code needs to see a type from a library module, export just that module: 

kotlin {
    listOf(iosX64(), iosArm64(), iosSimulatorArm64()).forEach { target ->
        target.binaries.framework {
            baseName = "ComposeApp"
            isStatic = true
            // Only if Swift needs these types directly
            export(projects.feature.games.domain)
        }
    }

    sourceSets.commonMain.dependencies {
        implementation(projects.feature.games.presentation)
        implementation(projects.feature.favorites.presentation)
        api(projects.feature.games.domain) // required for export()
    }
}

With Compose Multiplatform UI, Swift usually needs almost nothing: one function that returns the root view controller.

07 Common mistakes

Mistake Feature modules depending on each other.

It starts with one import and ends with circular dependencies and a build that recompiles half the app. Move the shared piece to core, and let the app module handle navigation between features.

Mistake A "core" module that holds everything.

If core contains networking, database, UI components and business logic, you've just renamed shared. Keep core modules small and focused on one concern each.

Mistake DTOs leaking into the UI.

If a screen uses GameDto straight from the API, every backend change breaks your UI. Map DTOs to domain models inside the data module.

Mistake Splitting too early.

Thirty modules for a five-screen app adds Gradle overhead with no benefit. Start with features, then split layers when a feature grows.

08 Your KMP modularization checklist

  • Features split by feature, then by layer when they grow
  • Shared infrastructure in small, focused core modules
  • No feature-to-feature dependencies
  • Domain modules are pure Kotlin and depend only on core:common
  • Convention plugins in build-logic instead of copy-pasted Gradle
  • One Koin module per module, assembled in the app
  • One iOS framework, from the app module
